# 数据验证技能

交付前质量保证检查清单、常见数据分析陷阱、结果完整性检查和可复现性文档标准。

## 交付前质量保证检查清单

在与利益相关者分享任何分析之前，请完成此检查清单。

### 数据质量检查

- [ ] **来源验证**：确认使用了哪些表/数据源。它们是这个问题的正确选择吗？
- [ ] **时效性**：数据对分析来说足够新。注明"截至"日期。
- [ ] **完整性**：时间序列或分群中没有意外的间隔。
- [ ] **空值处理**：检查关键列的空值率。空值处理得当（排除、填充或标记）。
- [ ] **去重**：确认没有因错误连接或重复源记录而导致的重复计数。
- [ ] **筛选验证**：所有 WHERE 子句和筛选器都正确。没有意外的排除。

### 计算检查

- [ ] **聚合逻辑**：GROUP BY 包含所有非聚合列。聚合级别与分析粒度匹配。
- [ ] **分母正确性**：比率和百分比计算使用正确的分母。分母非零。
- [ ] **日期对齐**：比较使用相同的时间段长度。部分周期被排除或注明。
- [ ] **连接正确性**：JOIN 类型适当（INNER vs LEFT）。多对多连接没有膨胀计数。
- [ ] **指标定义**：指标与利益相关者的定义一致。任何偏差都已注明。
- [ ] **小计求和**：部分在预期处加起来等于整体。如果不等于，解释原因（如重叠）。

### 合理性检查

- [ ] **量级**：数字在合理范围内。收入不是负数。百分比在 0-100% 之间。
- [ ] **趋势连续性**：时间序列中没有无法解释的跳跃或下降。
- [ ] **交叉引用**：关键数字与其他已知来源（仪表板、以前的报告、财务数据）匹配。
- [ ] **数量级**：总收入在正确的范围内。用户数与已知数字匹配。
- [ ] **边缘情况**：边界情况会发生什么？空分群、零活动期、新实体。

### 展示检查

- [ ] **图表准确性**：条形图从零开始。轴有标签。面板间比例一致。
- [ ] **数字格式**：适当的精度。一致的货币/百分比格式。需要时有千位分隔符。
- [ ] **标题清晰**：标题陈述洞察，而不仅仅是指标。指定日期范围。
- [ ] **注意事项透明**：已知限制和假设明确说明。
- [ ] **可复现性**：其他人可以根据提供的文档重新创建此分析。

## 常见数据分析陷阱

### 连接爆炸

**问题**：多对多连接悄悄地乘以行数，膨胀计数和总和。

**如何检测**：
```sql
-- 检查连接前后的行数
SELECT COUNT(*) FROM table_a;  -- 1,000
SELECT COUNT(*) FROM table_a a JOIN table_b b ON a.id = b.a_id;  -- 3,500（糟糕）
```

**如何预防**：
- 始终在连接后检查行数
- 如果计数增加，调查连接关系（它真的是 1:1 还是 1:多？）
- 通过连接计数实体时使用 `COUNT(DISTINCT a.id)` 而不是 `COUNT(*)`

### 生存偏差

**问题**：只分析今天存在的实体，忽略那些被删除、流失或失败的实体。

**示例**：
- 分析"当前用户"的用户行为会遗漏流失的用户
- 查看"使用我们产品的公司"会忽略那些评估后离开的公司
- 研究"成功"结果的属性而不考虑"不成功"的结果

**如何预防**：在得出结论之前问"谁不在这个数据集中？"

### 不完整周期比较

**问题**：将部分周期与完整周期进行比较。

**示例**：
- "1月收入是 $500K，而 12 月是 $800K"——但 1 月还没结束
- "这周的注册下降了"——周三检查的，与完整的上周比较

**如何预防**：始终筛选到完整周期，或比较同月同日 / 相同天数。

### 分母变化

**问题**：分母在周期之间变化，使比率无法比较。

**示例**：
- 转化率提高是因为您改变了"合格"用户的计算方式
- 流失率变化是因为"活跃"的定义被更新了

**如何预防**：在所有比较周期使用一致的定义。注明任何定义变化。

### 平均值的平均值

**问题**：当组大小不同时，对预先计算的平均值求平均会得到错误的结果。

**示例**：
- A 组：100 个用户，平均收入 $50
- B 组：10 个用户，平均收入 $200
- 错误：平均值的平均值 = ($50 + $200) / 2 = $125
- 正确：加权平均 = (100*$50 + 10*$200) / 110 = $63.64

**如何预防**：始终从原始数据聚合。永远不要对预聚合的平均值求平均。

### 时区不匹配

**问题**：不同数据源使用不同时区，导致不对齐。

**示例**：
- 事件时间戳使用 UTC vs 面向用户的日期使用本地时间
- 使用不同截止时间的日汇总

**如何预防**：分析前将所有时间戳标准化为单一时区（推荐 UTC）。记录使用的时区。

### 分群中的选择偏差

**问题**：分群是根据您正在测量的结果定义的，造成循环逻辑。

**示例**：
- "完成引导的用户留存率更高"——显然，他们自我选择了
- "活跃用户创造更多收入"——他们通过创造收入成为活跃用户的

**如何预防**：根据处理前的特征定义分群，而不是结果。

## 结果完整性检查

### 量级检查

对分析中的任何关键数字，验证它通过"气味测试"：

| 指标类型 | 完整性检查 |
|---|---|
| 用户数 | 这与已知的 MAU/DAU 数字匹配吗？ |
| 收入 | 这与已知的 ARR 量级正确吗？ |
| 转化率 | 这在 0% 到 100% 之间吗？与仪表板数字匹配吗？ |
| 增长率 | 50%+ 的月环比增长是否现实，或者有数据问题？ |
| 平均值 | 考虑到您对分布的了解，平均值合理吗？ |
| 百分比 | 分群百分比加起来约等于 100% 吗？ |

### 交叉验证技术

1. **用两种不同方式计算相同指标** 并验证它们匹配
2. **抽查单个记录**——挑选几个特定实体并手动追踪其数据
3. **与已知基准比较**——与发布的仪表板、财务报告或以前的分析匹配
4. **逆向工程**——如果总收入是 X，每用户收入乘以用户数是否大约等于 X？
5. **边界检查**——当您筛选到单天、单用户或单类别时会发生什么？这些微观结果合理吗？

### 需要调查的危险信号

- 任何周期环比变化超过 50% 且没有明显原因的指标
- 计数或总和是精确的整数（表明筛选或默认值问题）
- 比率恰好为 0% 或 100%（可能表示数据不完整）
- 完美确认假设的结果（现实通常更混乱）
- 跨时间段或分群的相同值（表明查询忽略了某个维度）

## 可复现性文档标准

### 分析文档模板

每个非平凡的分析都应包含：

```markdown
## 分析：[标题]

### 问题
[正在回答的具体问题]

### 数据来源
- 表：[schema.table_name]（截至 [日期]）
- 表：[schema.other_table]（截至 [日期]）
- 文件：[文件名]（来源：[从哪里来的]）

### 定义
- [指标 A]：[如何精确计算]
- [分群 X]：[如何精确确定成员资格]
- [时间段]：[开始日期] 到 [结束日期]，[时区]

### 方法论
1. [分析方法的第 1 步]
2. [第 2 步]
3. [第 3 步]

### 假设和限制
- [假设 1 及其合理性]
- [限制 1 及其对结论的潜在影响]

### 主要发现
1. [发现 1 及支持证据]
2. [发现 2 及支持证据]

### SQL 查询
[所有使用的查询，带注释]

### 注意事项
- [读者在采取行动之前应该知道的事情]
```

### 代码文档

对于可能被重用的任何代码（SQL、Python）：

```python
"""
分析：月度群组留存
作者：[姓名]
日期：[日期]
数据来源：events 表、users 表
上次验证：[日期]——结果与仪表板匹配，误差在 2% 以内

目的：
    根据首次活动日期计算月度用户留存群组。

假设：
    - "活跃"意味着当月至少有一个事件
    - 排除测试/内部账户（user_type != 'internal'）
    - 全程使用 UTC 日期

输出：
    群组留存矩阵，行为 cohort_month，列为 months_since_signup。
    值为留存率（0-100%）。
"""
```

### 分析的版本控制

- 将查询和代码保存在版本控制（git）或共享文档系统中
- 注明使用的数据快照日期
- 如果使用更新的数据重新运行分析，记录更改内容及原因
- 链接到重复分析的先前版本以进行趋势比较
