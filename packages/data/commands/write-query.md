# /write-query - 编写优化的 SQL

> 如果你看到不熟悉的占位符或需要检查已连接的工具，请参阅 [CONNECTORS.md](../CONNECTORS.md)。

根据自然语言描述编写 SQL 查询，针对你特定的 SQL 方言进行优化并遵循最佳实践。

## 用法

```
/write-query <描述你需要什么数据>
```

## 工作流程

### 1. 理解请求

解析用户的描述以识别：

- **输出列**：结果应包含哪些字段？
- **过滤条件**：哪些条件限制数据（时间范围、细分、状态）？
- **聚合**：是否有 GROUP BY 操作、计数、求和、平均值？
- **连接**：是否需要组合多个表？
- **排序**：结果应如何排序？
- **限制**：是否有 top-N 或采样要求？

### 2. 确定 SQL 方言

如果用户的 SQL 方言未知，询问他们使用哪种：

- **PostgreSQL**（包括 Aurora、RDS、Supabase、Neon）
- **Snowflake**
- **BigQuery**（Google Cloud）
- **Redshift**（Amazon）
- **Databricks SQL**
- **MySQL**（包括 Aurora MySQL、PlanetScale）
- **SQL Server**（Microsoft）
- **DuckDB**
- **SQLite**
- **其他**（询问具体信息）

在同一会话中记住方言以供后续查询使用。

### 3. 发现 Schema（如已连接数据仓库）

如果已连接数据仓库 MCP 服务器：

1. 根据用户描述搜索相关表
2. 检查列名、类型和关系
3. 检查影响性能的分区或聚集键
4. 查找可能简化查询的预构建视图或物化视图

### 4. 编写查询

遵循以下最佳实践：

**结构：**
- 当查询有多个逻辑步骤时，使用 CTE（WITH 子句）提高可读性
- 每个 CTE 对应一个逻辑转换或数据源
- 使用描述性命名 CTE（例如 `daily_signups`、`active_users`、`revenue_by_product`）

**性能：**
- 生产查询中永远不要使用 `SELECT *`——只指定需要的列
- 尽早过滤（将 WHERE 子句尽可能靠近基础表）
- 可用时使用分区过滤（特别是日期分区）
- 对于大结果集的子查询，优先使用 `EXISTS` 而非 `IN`
- 使用适当的 JOIN 类型（当 INNER JOIN 正确时不要使用 LEFT JOIN）
- 当 JOIN 或窗口函数可行时，避免相关子查询
- 注意爆炸性连接（多对多）

**可读性：**
- 为非明显的逻辑添加解释"为什么"的注释
- 使用一致的缩进和格式
- 用有意义的短名称别名表（不仅仅是 `a`、`b`、`c`）
- 将每个主要子句放在单独的行上

**方言特定优化：**
- 应用方言特定的语法和函数（详见 `sql-queries` 技能）
- 使用方言适当的日期函数、字符串函数和窗口语法
- 注意任何方言特定的性能特性（如 Snowflake 聚集、BigQuery 分区）

### 5. 展示查询

提供：

1. **完整查询**：在带语法高亮的 SQL 代码块中
2. **简要说明**：每个 CTE 或部分做什么
3. **性能注意事项**（如相关）：预期成本、分区使用、潜在瓶颈
4. **修改建议**——如何针对常见变化进行调整（不同时间范围、不同粒度、额外过滤）

### 6. 提供执行选项

如果已连接数据仓库，提供运行查询并分析结果的选项。如果用户想自己运行，查询已准备好可复制粘贴。

## 示例

**简单聚合：**
```
/write-query 过去30天按状态统计订单数量
```

**复杂分析：**
```
/write-query 群组留存分析——按注册月份对用户分组，然后显示注册后1、3、6和12个月仍然活跃（至少有一个事件）的百分比
```

**性能关键：**
```
/write-query 我们有一个5亿行的事件表，按日期分区。找出过去7天事件数量最多的前100个用户及其最近的事件类型。
```

## 提示

- 提前说明你的 SQL 方言以立即获得正确的语法
- 如果你知道表名，包含它们——否则 Claude 会帮你找到
- 如果需要查询是幂等的（可安全重复运行）或一次性的，请说明
- 对于定期查询，说明是否应该针对日期范围参数化
